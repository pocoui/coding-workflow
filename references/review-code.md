# Code 审查 — P0/P1/P2 分类表

## 1. 审查场景说明

本文件定义 **代码变更审查** 专用分类体系。审查对象为本次 vId 所有 commit 的实际代码变更（git diff），审查产物为 `.ai-coding/temp/{vId}/code-suggest.md`（校验建议文件）。

审查时机：所有 plan steps 执行完成后、用户验收前。

与 review-spec.md / review-plan.md 的差异：
- 审查对象从"文档"变为"实际代码变更"
- 增加"安全漏洞"维度（P0）
- 增加"代码重复/坏味道"维度（P1）
- 对齐 spec.acceptance 和 spec.constraints 进行符合性检查

## 2. P0/P1/P2 分类表

| 等级 | 类别 | 描述 |
|------|------|------|
| 🔴 P0 | 功能遗漏 | spec.acceptance 中的验收标准未全部实现，或 plan.json 中的步骤目标未达成 |
| 🔴 P0 | 安全漏洞 | XSS/CSRF/SQL注入/路径遍历/敏感信息泄露/未授权访问等安全缺陷 |
| 🔴 P0 | 破坏已有功能 | 已有测试失败、行为变更或回归，未声明的 breaking change |
| 🔴 P0 | 数据丢失风险 | 迁移脚本不可逆、数据操作未做幂等、缺少事务保护 |
| 🔴 P0 | 约束冲突 | 实现与 spec.constraints 中的技术/业务/安全约束直接冲突 |
| 🟡 P1 | 边界未处理 | 空值、并发、超时、大量数据等边界情况未覆盖 |
| 🟡 P1 | 代码重复 | 多处复制粘贴相同逻辑，未提取公共方法 |
| 🟡 P1 | 逻辑混乱 | 嵌套过深、函数过长、命名不清晰、职责混杂 |
| 🟡 P1 | 错误处理不当 | 吞掉异常、错误信息不明确、缺少必要的 try-catch |
| 🟡 P1 | 与约束部分偏离 | 实现方向与 spec.constraints 一致但细节有偏差，不影响核心功能 |
| 🟢 P2 | 可维护性建议 | 可提取公共逻辑、可简化条件判断、可改善命名 |
| 🟢 P2 | 性能优化 | 可优化但不影响正确性（如减少不必要的循环、懒加载） |
| 🟢 P2 | 风格不一致 | 与项目现有代码风格（命名、缩进、注释）不一致 |

## 3. 检查重点（Reviewer 角色注入用）

Reviewer 角色启动时，将以下检查重点注入 prompt，指导审查方向：

- 对照 spec.json 的 acceptance 数组，逐条确认是否已实现
- 对照 spec.json 的 constraints 数组，确认技术/业务/安全约束是否遵守
- 对照 plan.json 的 steps，确认每步的 goal 和 verification 是否达成
- 检查安全维度：输入校验、输出编码、权限控制、敏感信息处理
- 检查边界情况：空值、并发、超时、大量数据
- 检查错误处理：异常是否被正确捕获和传递
- 检查代码质量：重复逻辑、函数复杂度、命名清晰度
- 检查是否有未声明的 breaking change（删除/修改已有公开接口）
- 检查数据操作：迁移脚本是否可逆、是否幂等、是否有事务保护

## 4. 判断标准

主流程判断 code review 可以退出循环的标准：

- **P0 列表为空** — 无功能遗漏、无安全漏洞、无已有功能破坏、无数据丢失风险、无约束冲突
- **P1 列表中无"边界未处理"或"错误处理不当"类的实质性问题** — 仅含代码风格或可维护性建议，可退出循环

> 与 spec/plan 审查一致：P0 必须修复（启动 execution 修补模式），P1 由用户决定是否修复，P2 仅展示不强制。
