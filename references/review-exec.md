# 执行/代码审查 — P0/P1/P2 分类表

## 1. 审查场景说明

本文件定义 **执行/代码产物审查** 专用分类体系。审查对象为 Execution 角色产出的代码变更，审查产物为 `exec-suggest.md`（输出目录由具体 skill 定义，因执行产物散落在项目目录中，非集中管理）。

本分类与 spec/plan 审查完全不同，是一套专门面向代码的完整分类体系。"方案缺陷"已不适用（方案由 spec 确定），核心关注点是正确性和安全性。

## 2. P0/P1/P2 分类表

| 等级 | 类别 | 描述 |
|------|------|------|
| 🔴 P0 | 功能不正确 | 实现与 spec 不符，或核心逻辑存在明显错误 |
| 🔴 P0 | 安全漏洞 | 存在 SQL 注入、XSS、敏感信息泄露、认证绕过等安全风险 |
| 🔴 P0 | 破坏已有功能 | 修改导致未预期的模块或已有功能受损（需验证测试覆盖） |
| 🔴 P0 | 测试缺失 | 核心逻辑（新功能、关键分支）无对应测试覆盖 |
| 🟡 P1 | 错误处理不完善 | 网络超时、空值、非法输入等边界错误未处理或处理不当 |
| 🟡 P1 | 性能隐患 | N+1 查询、无必要的重复计算、未使用缓存、大对象未释放 |
| 🟡 P1 | 可维护性 | 逻辑过于复杂、缺少必要注释、不直观的控制流 |
| 🟡 P1 | 测试不充分 | 测试仅覆盖 happy path，未覆盖异常路径或边界条件 |
| 🟢 P2 | 代码风格 | 命名惯例、格式化、导入顺序等风格问题 |
| 🟢 P2 | 重构机会 | 可提取的公共逻辑、可简化的条件表达式（不影响正确性） |
| 🟢 P2 | 过度设计 | 抽象的层级过多、预留的扩展点当前不需要 |

> 与文档审查的差异：这是一套专门面向代码的完整分类，与 spec/plan 审查完全不同。"方案缺陷"已不适用（方案由 spec 确定）；核心关注点是正确性和安全性。

## 3. 检查重点（Reviewer 角色注入用）

Reviewer 角色启动时，将以下检查重点注入 prompt，指导审查方向：

- 实现是否与 spec 规格一致（功能正确性）
- 是否存在安全漏洞（输入校验、认证、数据保护）
- 是否有未处理的错误或异常路径
- 是否引入不必要的依赖或副作用
- 测试是否覆盖核心逻辑和边界条件
- 代码是否可读、可维护
- 是否存在明显的性能问题

## 4. 判断标准

主流程判断执行产物可以退出循环的标准：

- **P0 列表为空** — 无阻塞问题（功能正确、无安全漏洞、不破坏已有功能、核心逻辑有测试覆盖）
- **P1 列表中无"功能错误"或"安全"类的实质性问题** — 仅含性能或可维护性建议，可退出循环
