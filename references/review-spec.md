# Spec 审查 — P0/P1/P2 分类表

## 1. 审查场景说明

本文件定义 **Spec 规格文档审查** 专用分类体系。审查对象为 `.ai-coding/temp/{vId}/spec.md`（规格文档），审查产物为 `.ai-coding/temp/{vId}/spec-suggest.md`（校验建议文件）。

## 2. P0/P1/P2 分类表

| 等级 | 类别 | 描述 |
|------|------|------|
| 🔴 P0 | 内容遗漏 | 关键的功能规格、边界条件、异常流程缺失，导致开发无法正常推进 |
| 🔴 P0 | 范围缺失 | scope 字段缺失或 inScope/outOfScope 为空，无法界定需求边界 |
| 🔴 P0 | 场景缺失 | userScenarios 缺失或为空，无法理解用户角色与行为路径 |
| 🔴 P0 | 约束缺失 | constraints 缺失或为空，缺乏技术/业务约束说明，plan 可能选错技术栈 |
| 🔴 P0 | 逻辑矛盾 | 同一 spec 中存在相互冲突的功能描述、技术选型或数据定义 |
| 🔴 P0 | 方案缺陷 | 技术方案明显不可行、选型错误，会导致后续工作走错方向 |
| 🔴 P0 | 不可验证 | 验收标准缺失或模糊，开发完成后无法判断是否达标 |
| 🟡 P1 | 描述不清 | 表述含糊、有歧义，多个读者可能产生不同理解 |
| 🟡 P1 | 边界缺失 | 输入校验、空状态、并发、超时等边界条件未覆盖 |
| 🟡 P1 | 上下文断裂 | 依赖外部系统或前置假设但不做说明，读者无法理解上下文 |
| 🟡 P1 | 格式堆砌 | 结构化文本字段（background/goal/description 等）未拆分为 summary+details，写成单个长段落 |
| 🟡 P1 | 不完整 | 某部分有改进空间，但当前版本尚可工作 |
| 🟢 P2 | 措辞润色 | 表述可更精炼或清晰，但不影响理解 |
| 🟢 P2 | 格式风格 | 排版、标记风格不一致 |
| 🟢 P2 | 过度设计 | 为不确定的未来做的提前扩展 |

## 3. 检查重点（Reviewer 角色注入用）

Reviewer 角色启动时，将以下检查重点注入 prompt，指导审查方向：

- 范围边界是否明确（scope.inScope 和 scope.outOfScope 是否完整列出）
- 用户场景是否完整（userScenarios 是否覆盖所有角色与核心行为路径）
- 技术约束与业务假设是否明确（constraints 是否覆盖技术/业务/兼容性/安全/性能五类）
- 功能规格是否完整覆盖用户需求
- 结构化文本字段（background/goal/features[].description/technicalApproach）是否拆分为 summary+details，禁止单个长段落
- 技术方案是否可行且合理（选型理由、替代方案对比）
- 边界条件和异常场景是否覆盖（输入校验、空值、网络超时、并发冲突）
- 非功能需求是否明确（性能指标、安全要求、兼容性）
- 验收标准是否可验证（不应出现"系统应流畅运行"这类模糊表述，每条≤200字）
- 涉及的文件结构是否完整列出

## 4. 判断标准

主流程判断 spec 可以退出循环的标准：

- **P0 列表为空** — 无阻塞问题（无遗漏、无矛盾、方案可行、验收标准可衡量、scope/constraints/userScenarios 均完整）
- **P1 列表中无"内容缺失"或"格式堆砌"类的实质性问题** — 仅含措辞或格式建议，可退出循环
